## Model and caller authority

The supported model remains **local-first, one trusted OS operator**, with separate server-configured kubeconfig connections. It is not an Internet-facing per-user SaaS or a sandbox against malware running under the same OS account. `API_TOKEN` gates access to the app; it does not mint a Kubernetes identity. Each connection uses its configured kubeconfig identity or in-cluster ServiceAccount, and real Kubernetes RBAC/admission remains the final authority.

Browser input is untrusted even when it names a context, harbor, namespace, resource, provider operation or Pod command. Browser-selected names are addresses, not proof of authorization. Operator flags/env, kubeconfig/plugin definitions, STATIC_DIR and provider binary/config paths are a **separate trusted host configuration boundary**. A malicious trusted auth plugin/provider binary already executes with the backend OS user's authority; these are not made safe by fixed browser request schemas.

The existing ASVS5.0.0 V8.1.1/V8.1.2 and API9:2023 mappings in `docs/RELEASE_THREAT_MODEL.md` are framework references for this inventory, not compliance certification. No new external standards verification was performed in this offline task.

## Host/transport boundaries that must not be overstated

- The standalone listener is HTTP, not native TLS or Unix-domain socket based. Loopback is a deployment control, not immunity from a malicious local webpage. Exact Host/Origin/nonce/cookie guards are necessary. Remote use needs the documented loopback SSH/kubectl tunnel/explicit operator security boundary; arbitrary proxy forwarded headers are not trusted. No Unix socket ACL claim is made.
- Kubernetes API TLS and Hubble mTLS are separate connections. A good Hubble client certificate is not Kubernetes namespace permission. TLS does not certify collector semantics, source image advisories or safe browser data exposure.
- Hubble resolves its executable through operator PATH; it does not pin executable file content/signature or sandbox the trusted binary. Minikube provider checks LookPath availability but retains configured Binary string; subsequent CommandContext and bare `docker` inspect can use the operator PATH. Its CLI environment mostly inherits the operator environment, unlike Hubble's allowlist. These are explicit host trust/TEST12.08 boundaries, **not a newly reproduced remote command-injection defect**. An absolute reviewed executable is operational hardening; active product code must not be described as enforcing an immutable binary everywhere.
- Provider directory creation/file modes do not prove all existing directory, symlink, hostile-local-file or crash-atomicity cases safe. Workspace Store has explicit private-dir/regular-file checks; provider state/TLS paths have different checks. CAT12 filesystem/PATH tests remain separate. Same-OS-account malware is outside the local-first sandbox claim.
- Configured admin kubeconfig is an admin delegation by the local operator. Browser auth does not derive the OS/browser person's independent Kubernetes RBAC. Separate connections with different credentials must remain separate; UI labels and same server URL cannot collapse that distinction.
- Existing docs contain historical generic-session phrasing; current workspace operator key includes harbor/tab. Source, not stale broad cross-tab prose, defines the mapped current boundary. No documentation phrasing is used as runtime test proof.
